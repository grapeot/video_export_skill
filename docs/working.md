## Lessons Learned

- DaVinci Resolve Studio's native `fusionscript.so` library can emit non-JSON text to stdout during attach. Isolating Resolve scripting inside `python -m video_export.resolve_worker <result_file>` keeps the parent CLI's single-JSON stdout contract clean.
- Resolve Studio coerces tiny requested timeline resolutions up to its minimum supported dimensions (`256x256` in live smoke testing, where the scratch timeline, ProRes 422 HQ master, and Compressor HEVC target all measured `256x256`). Never assume synthetic input clip dimensions equal the timeline or output dimensions; always read actual timeline and `ffprobe` stream dimensions.
- Calling `resolve.Quit()` over the scripting API cleanly exits an owned headless `Resolve -nogui` process with exit code `0` (whereas `SIGTERM` triggers the macOS Crash Reporter). If a render times out while `IsRenderingInProgress()` is true, do not call `Quit()` or kill the process; leave the render running and retain `resolve-job.json` and `manifest.json` for manual inspection.
- Resolve's `Project` API has no `GetRenderSettings()` or `GetCurrentRenderPreset()` method and no dirty-state query. `resolve render --execute` mutates active Deliver settings in memory (`SetCurrentTimeline`, `LoadRenderPreset`, `SetCurrentRenderMode(1)`, optional `SetCurrentRenderFormatAndCodec`, `SetRenderSettings`) and never calls `SaveProject()`, but Resolve's own Live Save feature may persist those changes if enabled.
- Dry-runs validate configuration, Compressor `.compressorsetting` XML, and output path collisions locally without connecting to Resolve or writing state manifests. Existence of a Resolve project, timeline, or Deliver preset is verified only when running `resolve inspect` or `--execute`.
- Read-only `resolve inspect --project NAME` (and `render --execute`) may call `LoadProject(NAME)` only when no project or `"Untitled Project"` is loaded (or in an owned `--headless` instance), and only searches the current Resolve database folder (`GetProjectListInCurrentFolder`).
- `--reuse-master MANIFEST` takes an explicit prior `manifest.json` path and compares the SHA-256 identity of the Resolve configuration plus the master file's on-disk metadata fingerprint (`path`, `size`, `mtime_ns`). This avoids hashing multi-gigabyte masters on retry, but it does not hash media contents or detect edits inside the Resolve project; users must run a fresh render after editing a timeline.
- Apple Compressor CLI (`/Applications/Compressor.app/Contents/MacOS/Compressor`) requires `-locationpath` to be a complete file path, requires `-format json` immediately after `-monitor` (`-monitor -format json -batchid ID -once`), and may emit diagnostic text around JSON output.
- In Compressor `-monitor` payloads, child job entries or other batches may report `status: "Successful"` while the target batch is still `Waiting` or `Processing`. `batch_status()` must match only the requested `batchID` and verify every target output file via `lsof`, byte-size stability, and `ffprobe` after the batch reaches `Successful`.
- Compressor `.compressorsetting` XML stores `<frame-rate>` values in `R`-prefixed integer or rational forms such as `R60/1` and `R30000/1001`, where `float()` fails. Strip whitespace before checking follow-source sentinels. `rates.rate()` parses decimal, rational, and `R`-prefixed strings as exact `Fraction` values and maps conventional rounded NTSC labels (`23.976`, `29.97`, `59.94`, `119.88`) to exact `1001`-denominator rationals; conflict checks use `< 0.01` fps tolerance for rounded NTSC labels.
- With `--max-frame-rate` (or `[compressor] max_frame_rate`), cadence selection uses a literal numeric ceiling rather than forcing every output to `60` or leaving presets on blind `Automatic`: verify the source first, keep the exact source rate when at or below the cap (`23.976`, `24`, `29.97`, `30`, `59.94`, `60` remain themselves for cap `60`), and repeatedly halve above-cap rates (`119.88 -> 59.94`, `120 -> 60` under cap `60`; a literal `59.94` cap on integer `60`/`120` selects `30` to preserve integer cadence without exceeding the ceiling, so do not equate `59.94` with `60`). Under `--execute`, write private derived `.compressorsetting` files inside the run state directory that replace **only** the single `<frame-rate>...</frame-rate>` text inside the sole `<video-encode>` element byte-for-byte (`R<num>/<den>`) and confirm via parsed XML readback, leaving `data-rate`, `auto-purpose`, `auto-bit-rate-purpose`, color, HDR, Dolby Vision, and geometry fields untouched and never overwriting original presets. Do not equate raw XML `data-rate` values to measured output Mbps or assume lowering frame rate halves bitrate.
- In `.compressorsetting` XML, a negative `<automatic width="..."/>` value can encode automatic geometry even when `<bounds>` has `"-100"`. `compressor presets` reports `automatic_geometry` separately and sets `resolution_mode: "automatic_geometry"` when applicable. Never claim `follow_source` from `<bounds>` alone or infer actual dimensions from preset filenames; always probe rendered outputs with `ffprobe` (and note that a single shared `--expect-resolution` flag cannot assert distinct dimensions across mixed-resolution targets).
- Long CLI-only Apple Compressor batches can fail mid-run with `Failed: 2x job controller down` when `CompressorHelper` exits and its `JobControllerService` is terminated during active work (observed in macOS unified logs). Keeping the `Compressor.app` GUI open and repeating the batch with the identical media, codecs, frame rate, and bitrate/Dolby Vision settings succeeded as an observed operational recovery (not a proven universal root cause; the CLI does not auto-launch the GUI). On this error, inspect batch status and unified logs, preserve the master file, leave existing queues and settings untouched, never run `-resetBackgroundProcessing` or mass-cancel jobs, optionally open/keep `Compressor.app` running, and retry only terminal failed jobs when their output destination paths are still absent.
- In DaVinci Resolve Studio, `DuplicateTimeline()` inherits the original timeline's frame rate, and `Timeline.SetSetting("timelineFrameRate", ...)` may return `False` even on a newly created empty timeline. Never ignore `False` or mutate the original timeline in place as a workaround. For a simple cut-only timeline (empirically verified on a simple cut-only timeline, not a generic CLI migration feature), export FCPXML, change **only** the sequence `<format>` `frameDuration` from the source rate to the intended rate while preserving rational-time offsets and durations, import with source-media reuse, then call `CopyGrades` and copy/read back Inspector properties as needed. Validate every clip's start, duration, source in-point, media identity, audio layout, grade and color settings, and total duration while keeping the original timeline and a local backup. Do not generalize this procedure to Fusion compositions, keyframes, transitions, retimes, groups, or arbitrary projects, and remember that metadata equivalence alone is not subjective visual HDR validation.
